## 1. 개요·로드맵

### 1.1 한 줄 목표
LangGraph·Bedrock 기반의 범용 여행 계획·조언 에이전트(CLI)를 만든다. 사용자가 넣은 URL을 미들웨어가 여행 관련도로 판정해 user_id별 영구 벡터DB에 저장·재사용하고, 출처를 밝힌 일정표·파이썬 예산 계산·날씨/환율 조회·단발성 Q&A를 제공하며, 이후 MCP·웹으로 확장 가능한 구조로 설계한다.

### 1.2 대상 사용자와 사용 장면
- 여행 일정을 짜거나 여행 관련 정보를 묻는 일반 사용자
- 사용 예
  - "오사카 3박4일, 1인 100만원으로 일정 짜줘"
  - "이 블로그 참고해서 일정 짜줘 https://..."
  - "A 관광지 아침에 사람 많아?"
  - "다음 주 도쿄 날씨 어때? 지금 엔화 환율은?"

### 1.3 로드맵
| 단계 | 내용 | 상태 |
|---|---|---|
| ① 에이전트 | LangGraph 에이전트 + CLI 대화 루프 | **1차 범위** |
| ② MCP | 에이전트 코어를 MCP 서버로 감싸 외부 클라이언트(Claude Desktop 등)에서 사용 (2.11) | **구현** (2026-11-06, 로컬 stdio) |
| ③ 웹 | 여행 계획 웹페이지. 이메일·비밀번호로 회원가입·로그인, 계정별 대화 여러 개와 저장 링크·기억 관리 (로그인 계정의 내부 ID = 에이전트 user_id) (2.10) | **구현됨** (2026-11-05) |
| + 장기 기억 | 같은 사용자의 다른 대화(thread)에서도 이름·여행 선호·답변 스타일을 기억 (1.5, 2.9) | **구현됨** (2026-11-05, CLI·웹) |

### 1.4 1차 범위
- 포함: 에이전트 코어(agent/tools/retriever), URL 수집 미들웨어, user_id별 영구 저장, CLI 실행
- 제외: MCP 서버, 플러그인 패키징, 웹페이지, 인증(회원가입/로그인), 장기 기억(thread 간 사용자 정보 기억), 유튜브·JS 렌더링·로그인 필요 페이지 수집

### 1.5 추후 추가 기능 (1차 완료·제출 후 시간 여유가 있을 때)
1차 범위(시나리오 4개 + 평가·제출물)를 모두 마친 뒤에만 진행한다. 하나씩 하고, 세부 규칙은 시작 직전에 정한다. 진행 순서는 장기 기억 → 웹페이지 → MCP 서버다(2026-11-05 변경: 처음엔 MCP가 웹보다 먼저였으나, 두 기능은 같은 에이전트 코어를 감싸는 별개 출입구라 서로 의존하지 않아 사용자 결정으로 웹을 앞당김). (→ OPEN_ISSUES.md, TASKS.md Phase 6)
1. **장기 기억**
   - 문제: 지금은 대화 기록이 thread 단위라, 같은 user_id라도 새 thread(`/new`, 새 실행)에서는 사용자가 알려준 이름·기본 정보를 기억하지 못한다.
   - 목표: user_id 단위로 사용자 정보를 저장해 모든 thread에서 쓴다. 예: 이름, 기본 출발지, 자주 가는 인원, 여행 선호(음식·숙소 등급·관심사).
   - 원칙: 사용자가 직접 말한 정보만 저장하고, 다른 user_id의 기억은 코드로 격리한다. 저장한 정보는 정보 부족 처리(2.2)의 기본값으로 쓸 수 있지만, 쓸 때는 '기억한 정보'임을 밝힌다. 사용자가 확인·삭제할 수 있어야 한다.
2. **MCP 서버** (로드맵 ②): 에이전트 코어를 MCP 서버로 감싸 외부 클라이언트(Claude Desktop 등)에서 쓸 수 있게 한다. → 2.11 (2026-11-06 설계 결정)
3. **웹페이지** (로드맵 ③): 회원가입·로그인과 로그인 유저별 RAG 자료 정리·관리 화면.

## 2. 기능 명세

### 2.1 URL 수집 (백그라운드 기능)
사용자가 따로 조작하지 않아도 동작하는 기능이다(링크마다 저장했는지, 못 썼다면 이유를 답변 끝에 알린다). 사용자가 URL과 함께 여행 질문을 하면 그 콘텐츠를 저장해 두고, 같은 턴과 이후 같은 사용자의 대화에서 답변 근거로 쓴다.
- **링크 처리 결과 안내** (2026-11-05 변경: 이전에는 참고하지 못한 링크만 알려, URL만 붙여넣은 사용자가 저장 여부를 알 수 없었다는 UX 평가 지적): 답변 끝에 '※ 링크 처리 결과' 목록을 붙인다. 저장한 링크는 '✔ 저장함: 제목 (URL)'(같은 내용 재입력은 '이미 저장됨', 내용이 바뀌면 '새 내용으로 갱신함'), 못 쓴 링크는 '✖ 못 씀: URL — 이유. 다음 행동'.
- **링크만 보낸 메시지**(URL과 '이거 저장해 줘' 같은 말뿐, 질문 없음): 에이전트(LLM)를 부르지 않고 "링크 N개를 저장해 두었습니다. 이 자료와 관련된 여행 질문을 하시면(예: '여기 운영시간 알려줘') 저장한 내용을 근거로 답해 드릴게요. 다음 대화에서도 쓸 수 있습니다."와 처리 결과 목록을 돌려준다. 하나도 저장하지 못했으면 "링크를 저장하지 못했습니다. 아래 안내를 확인해 주세요." 판정은 파이썬 규칙으로 한다.
- **저장 자료 목록 보기·개별 삭제** (2026-11-05 변경: 처음에는 1차 범위 밖으로 두고 '미지원' 안내만 했으나 사용자 결정으로 추가): 대화 중 CLI 명령으로 한다. 프로그램(파이썬)이 처리하고 LLM을 거치지 않으며, 현재 사용자의 자료만 보고 지운다.
  - `/saved`: 저장한 링크를 저장한 순서대로 번호·제목·URL·저장일과 함께 보여 준다. 없으면 "저장한 링크가 없습니다."
  - `/forget <번호>`: `/saved` 목록의 그 번호 링크를 지우고 "'제목' 링크를 지웠습니다. 이제 답변 근거로 쓰지 않습니다."라고 알린다. 번호가 없거나 범위 밖이면 지우지 않고 가능한 번호를 안내한다.
  - 대화로 목록·삭제를 요청하면 이 명령을 안내한다. 목록을 지어내거나 지운 척하지 않는다. 전체 삭제는 `--reset`.

- **실행 시점**: 매 턴 에이전트가 답하기 전에 항상 실행되는 고정 전처리 단계다. (LLM이 실행 여부를 정하지 않는다)
- **처리 흐름**
  1. 입력에서 URL 추출
  2. 페이지 수집 → 원본에서 텍스트만 추출
  3. 관련도 판정: 여행 관련도 점수(0~1)가 임계값 이상이고 **지시문 포함 의심**이 없으면 통과, 그 외 거절 (2.8)
     - 점수와 지시문 의심은 빠른 판정 모델이 본문 앞부분을 보고 매기고, 지시문은 프로그램(파이썬)이 본문 전체에서 한 번 더 찾는다. 둘 중 하나라도 의심하면 거절한다.
  4. 통과 시 해당 user_id 공간에 저장
  5. 저장한 콘텐츠는 **같은 턴 답변에도 바로** 근거로 사용
- **임계값**: 초기값 0.5. 조정 가능한 설정값이다.
- **거절**: 저장하지 않고 답변에도 쓰지 않으며, 답변 끝에 이유를 알린다. 시스템 로그에도 기록한다. (2026-11-05 변경: 이전에는 알리지 않음)
  - 관련도 낮음 → "여행 관련 내용이 아니라고 판단해 참고하지 않았습니다"
  - 지시문 의심 → "AI에게 하는 지시문으로 보이는 내용이 있어 안전을 위해 참고하지 않았습니다"
  - 안내는 프로그램이 답변 끝 '※ 링크 처리 결과' 목록에 '✖ 못 씀'으로 붙인다. (수집 실패·판정 실패·개수 초과도 같은 목록에 이유와 함께 표시)
  - 이유 뒤에는 사용자가 할 수 있는 다음 행동을 붙인다. (2026-11-05 추가: UX 평가에서 거절 안내가 막다른 길이라는 지적)
    - 관련도 낮음 → "여행 블로그나 관광 안내 페이지 링크를 보내 주세요"
    - 동영상 → "영상 설명이나 자막 내용을 글로 붙여 주시면 참고할게요" / 로그인 필요 → "게시물 내용을 글로 붙여 주시면 참고할게요" / PDF·이미지 → "필요한 내용을 글로 붙여 주시면 참고할게요" / 본문 없음 → "본문 내용을 글로 붙여 주시면 참고할게요"
    - 페이지 열기 실패·연결 실패·응답 지연 → "주소를 확인하거나 잠시 후 다시 보내 주세요"
    - 개수 초과 → "나머지 N개는 참고하지 않았으니 다음 메시지로 보내 주세요"
    - 지시문 의심에는 붙이지 않는다(우회 방법을 알려 주지 않기 위해). 시스템 장애 문구는 안내를 이미 담고 있다.
- **시스템 장애**(판정 LLM 호출 실패, 저장소·임베딩 오류): 저장하지 않고 로그를 남기며, 링크 문제가 아니라 우리 쪽 문제임을 알린다. → "링크에는 문제가 없지만, 지금 저장 기능에 일시적인 문제가 있어 참고하지 못했습니다. 잠시 후 같은 링크를 다시 보내 주세요" (2026-11-05 변경: 이전에는 판정 실패 "내용을 확인하지 못해 참고하지 않았습니다", 저장 오류 "처리 중 오류가 나 참고하지 않았습니다"라 사용자가 멀쩡한 링크를 포기하게 만든다는 UX 평가 지적)
  - 원인을 알 수 없는 처리 오류는 "처리 중 오류가 나 참고하지 않았습니다"로 알린다.
- **수집 실패**(로그인 필요, JS 렌더링, 유튜브 등): 사용자에게 읽지 못했다고 알리고, 기존 지식·웹 검색으로 답변을 계속한다. LLM 일반지식으로 답한 부분은 '출처 없음, 사용자 확인 필요'로 표시한다. (2.6)
  - 실패로 보는 경우: 동영상 사이트(유튜브 등), 로그인이 필요한 SNS(인스타그램 등), 웹페이지가 아닌 파일(PDF·이미지), 없는 페이지·접근 차단, 응답 시간 초과, 연결 실패, 본문이 거의 없는 페이지(자바스크립트로 그리는 페이지 등)
- **지원 범위**: 1차는 일반 HTML 텍스트 페이지. 유튜브 등 특수 소스를 나중에 추가할 수 있도록 수집기를 교체·확장 가능한 구조로 만든다.
  - 네이버 블로그 PC 주소는 본문을 읽을 수 없는 구조라, 수집할 때만 모바일 주소로 바꿔 읽는다. 저장·인용에는 사용자가 넣은 원래 주소를 쓴다.
- **같은 URL 재입력**(같은 user_id): 내용이 같으면 건너뛰고(관련도 판정도 다시 하지 않음), 바뀌었으면 판정을 다시 해 기존 내용을 새 내용으로 교체한다. 버전을 쌓지 않는다.
- **한계 조건** (조정 가능한 설정값)
  - 한 메시지에서 최대 **5개** URL까지 수집한다(동시 처리). 넘는 URL은 건너뛰고 "링크는 한 번에 5개까지만 참고합니다"라고 알린다. (2026-11-05 변경: 3개, 안내 없음 → 5개, 안내)
  - 수집 시간 한도 **15초**(리다이렉트·본문 받기를 합한 전체 시간). 넘으면 수집 실패. 받는 페이지는 최대 **3MB**이고, 넘으면 '페이지가 너무 커서 읽지 않았습니다'로 실패한다. (2026-11-05 R2: 전에는 바이트 사이 대기 시간이라, 조금씩 보내는 사이트에 끝없이 붙잡힐 수 있었다)
- **안전**(2026-11-05 R2, SSRF 방지): 내부망·로컬·클라우드 메타데이터 주소(예: 127.0.0.1, localhost, 10.x, 192.168.x, 169.254.169.254)는 열지 않는다. 리다이렉트로 옮겨 간 주소도 매번 다시 검사한다. 안내 문구는 '✖ 못 씀: … — 내부망·로컬 주소라 안전을 위해 열지 않았습니다. 공개된 웹페이지 주소를 보내 주세요'. 예외는 설정 허용 목록뿐이고(기본 비움), 평가 스크립트만 실행 중에 로컬 인젝션 테스트 페이지를 허용한다.
  - 본문이 **5만 자**를 넘으면 앞부분 5만 자만 저장한다. (잘린 사실은 로그에만)
  - 본문이 **200자** 미만이면 '본문 없음' 수집 실패.
- **응답 속도**: 처리 순서(수집 → 판정 → 저장 → 답변)는 지키되, 여러 URL은 동시에 처리하고 판정은 빠른 모델로 한다. 저장을 답변 뒤로 미루는 방식(백그라운드 저장)은 쓰지 않는다. (판정은 인젝션 방어라 생략할 수 없고, 본문을 직접 답변에 넣으면 토큰 비용이 커지며, 종료·평가 시 저장 완료를 보장하기 어렵기 때문)
- 구현 → SPEC.md 2.1

### 2.2 일정표 생성
- **입력 정보와 정보 부족 처리**
  - 일정에 필요한 정보: 목적지, 기간, 인원, 출발지, 예산, 예산 기준(1인/총액 — 인원 2명 이상이고 예산을 준 경우에만)
  - **당일치기·현지 일정은 출발지를 묻지 않는다** (2026-11-06 추가, TASKS Phase 8 S4): 당일치기(0박)이거나 사용자가 이미 목적지에 있거나 그곳에 산다고 하면 출발지는 필요 없는 항목이다. 묻지도 가정하지도 않고, 항공·장거리 이동은 일정·예산에 넣지 않는다. 사용자가 출발지를 말했으면 그대로 쓴다.
  - 빠진 항목이 있으면 **모두 한 번에 묶어 되묻는다.**
  - **취향도 처음 한 번 함께 묻는다** (2026-11-05 추가, 사용자 결정: 묻는 것이 귀찮더라도 맞춤 결과와 빠른 답변이 낫다): 꼭 가고 싶은 곳·이미 정한 일정, 여행 스타일(여유롭게/많이 보기), 관심사. 필수 항목이 다 있어도 묻는다. 에이전트가 일정에 도움이 된다고 판단한 질문(예: 동행의 걷기 부담, 숙소 위치)을 함께 더해도 된다. 대화나 장기 기억(2.9)으로 이미 알거나, 사용자가 "나머지는 알아서 해줘"처럼 맡겼으면 묻지 않는다. 답하지 않거나 모른다고 하면 다시 묻지 않고 에이전트가 정한다(일정표 맨 앞 '가정한 조건'에는 넣지 않는다). 받은 꼭 갈 곳·관심사 중심으로 검색 범위를 좁혀, 검색 시간·비용과 입력을 줄인다.
  - **한 대화에서 한 번 물어본 항목은 다시 묻지 않는다.** 물어본 뒤에도 답이 없으면(모른다·아직 안 정했다·알아서 해달라 포함) 아래 가정으로 진행한다. 같은 대화에서 **목적지가 바뀌면**(예: 오사카 → 대만) 새 여행으로 보고 처음부터 다시 확인한다. 목적지가 같으면(예: 인원만 변경) 다시 묻지 않는다.
  - 되물은 뒤 사용자가 아직 답하지 않았는데 에이전트가 스스로 가정으로 넘어가지 않는다. (사용자 메시지가 온 뒤에만 '물어봤다'로 본다)
  - 일정표가 아닌 단발성 질문(맛집·교통·날씨·환율 등)은 이 확인을 거치지 않는다.
  - 사용자 메시지에 일정 요청 표현(일정·코스 짜기·여행 계획 등)이 있으면 프로그램이 이 확인을 반드시 먼저 거치게 한다.
  - 사용자가 "알아서 해줘", "아직 몰라"처럼 정보를 주지 않으면 가정해서 일정을 만든다. 답변 앞에 **'가정한 조건'**을 표시한다.
    - 인원: 1명, 출발지: 인천 (조정 가능한 설정값)
    - 목적지·기간: 에이전트가 요청 맥락(예산·계절 등)에 맞게 정하고 가정임을 표시한다.
    - 예산: 가정하지 않는다. 예산 판정(2.3)만 생략한다.
    - 예산 기준: 총액(일행 전체)으로 가정한다.
- **필수 항목**
  1. 일자별·시간대별 장소
  2. 이동수단·소요시간
  3. 근거 출처 (RAG 문서 / 수집 URL / 웹 검색)
  4. 관광지 입장료: 출처가 있으면 '제목 + URL'과 함께 표시하고, 출처가 없으면 금액 옆에 '(출처 없음, 사용자 확인 필요)'를 붙여 표시한다. (2.6)
- **출력 형식**: 사용자에게는 읽기 쉬운 텍스트로 보여준다. 웹 단계(③)에서 화면에 다시 쓸 수 있는 형태로 만든다.
  - 일정표는 에이전트가 내용을 구조화해 넘기고, 프로그램이 정해진 형식으로 검증·렌더링한 결과를 **그대로** 보여준다. (에이전트가 글로 다시 쓰지 않는다)
  - 구성: 가정한 조건 → 제목·기간(날짜)·인원·출발지 → 일차별(날짜) 시간대·장소·이동수단·소요시간·출처, 출처 있는 입장료, 일차별 비용 → 참고 → 예산 요약 → (예산 초과 시) 예산 조정안 → 출처 목록
  - 예산을 **15% 넘게** 초과했는데 조정안이 없으면 일정표를 내보내지 않는다(프로그램이 막고 에이전트가 조정안을 채워 다시 만든다). 15% 이내 초과는 초과 금액만 알리고 그대로 진행한다(2.3).
  - 예산을 말했으면 일정표를 만들기 전에 예산을 먼저 계산해 초과 여부를 확인하고, 조정안이 필요하면 처음부터 넣는다. (2026-11-05 추가: 일정표를 다 만든 뒤 초과로 막혀 일정표 전체를 다시 만들느라 5박 일정에서 100초 이상 더 걸린 문제)
- 구현 → SPEC.md 2.2

### 2.3 예산 계산
정확한 견적이 아니라 **대략적 계산**으로, 예산 전후 금액으로 다녀올 수 있는 계획을 짜는 것이 목표다.
- **대상 항목**: 항공(왕복), 숙박, 식비, 현지 교통 등 예산 큰 항목
- **가격 근거 우선순위**
  1. 사용자가 입력에 준 값 (예: "항공권은 50만원")
  2. 웹 검색: 평균 항공권·숙박비 등을 검색해 금액 범위와 출처(제목 + URL)를 얻는다
  3. 출처를 못 찾은 항목: LLM 추정치를 허용하되 **'LLM 추정치(출처 없음, 사용자 확인 필요)'로 표시**한다
- 모든 금액은 최소~최대 **범위**로 다루고, 근거 표시(사용자 입력 / 출처 / LLM 추정치)와 '대략치'임을 함께 보여준다.
- **계산 원칙**: 모든 계산·판정은 LLM 암산이 아니라 코드로 한다. 항목별·일자별 합계(범위)를 내고, 인원·박 수·객실 수와 환율 환산을 반영한다.
- **비용 단위** (일수 = 박 수 + 1)
  - 1인 1회: 항공 왕복 → 인원만큼
  - 1인 1일: 식비·현지 교통 → 인원 × 일수
  - 객실 1박: 숙박 → 객실 수 × 박 수 (기본 2인 1실)
  - 일행 1회: 그대로 합산
  - 일행 1일: 렌터카 등 → 일수만큼
- **일자별 합계**: 특정 일차 비용은 그날, 1일당 비용은 매일, 숙박은 1~박수 일차에 나누고, 항공처럼 일자에 묶이지 않는 1회성 비용은 '여행 전체' 칸에 따로 보여준다.
- **추정치 허용 범위는 코드로 판정**: 출처 없는 LLM 추정치는 항공·숙박·식비·현지 교통 항목만 계산에 넣고, 입장료 등 그 밖의 추정치는 계산에서 빼고 금액을 표시하지 않는다. (2.6)
- **예산 기준**: 인원이 2명 이상인데 예산이 1인 기준인지 총액인지 불분명하면, 2.2에 따라 다른 빠진 항목과 묶어 되묻는다. 인원이 1명이면 묻지 않는다.
- **표시**: 합계는 일행 총액과 1인당 금액을 함께 보여준다. 예산 판정은 사용자가 말한 기준으로 한다.
- **예산 판정**(사용자가 입력에 예산을 명시한 경우에만): 총액 범위를 예산과 비교한다.
  - 최대값 ≤ 예산: 예산 안 (여유 금액 = 예산 − 최대값)
  - 예산 < 최대값 ≤ 예산 × 1.1: 예산 근접
  - 최대값 > 예산 × 1.1: 초과 금액(최대값 − 예산)과 함께 알린다
    - 초과 금액이 예산의 **15%를 넘으면** 숙박 등급·일정 조정 등 조정안을 제시한다. 15% 이내 초과는 조정안 없이 진행한다. (2026-11-05 변경, 사용자 결정: 너무 빡빡하게 막지 않는다. 이전에는 초과면 항상 조정안 필수)
    - **조정안의 효과는 프로그램이 다시 계산한다** (2026-11-06 추가, TASKS Phase 8 S1-2, 사용자 결정: 기존 도구 안에서 재계산): 조정안마다 '바꿀 비용 항목과 새 금액'을 받아 예산을 다시 계산하고 '항목 X → Y, 절감액(1인 금액), 적용 후 총액, 적용 후 판정(예산 안/근접/초과)'을 붙인다. 조정안이 둘 이상이면 '모두 적용하면' 결과도 붙인다. 바꾼 금액은 출처를 확인하지 않은 값이라 '출처 없음, 사용자 확인 필요'를 붙인다. 조정안 설명에 '예산 안으로 가능' 같은 판정·절감 단언이 있으면 지우고 바꾸는 내용만 남긴다.
  - 허용폭(10%)과 조정안 기준(15%)은 조정 가능한 설정값이다
- 실시간 항공·호텔 예약 API 연동은 1차 범위에서 제외한다.
- 구현 → SPEC.md 2.3

### 2.4 날씨·환율 조회
- 외부 API를 사용한다. 키 없는 무료 소스를 우선한다. (예: 날씨 Open-Meteo)
- 대상 지역: 전 세계 (국내+해외)
- **환율**
  - 키 없는 무료 공개 환율 API를 쓴다. (약 160개 통화)
  - 기준 통화: 원화(KRW)가 기본이다. 사용자가 다른 통화를 요청하면 그 통화로 계산·표시한다.
  - 하루 1회 갱신되는 참고 환율이므로 '대략치'로 다룬다.
  - **일반 답변의 원화 환산은 프로그램이 맞춘다** (2026-11-06 추가, TASKS Phase 8 S1-3, 사용자 결정: 후처리로 고침): 답변 속 '외화 가격(약 ○○원)'의 원화 값을 실제 환율로 다시 계산해, 3% 넘게 다르면 계산값으로 바꾼다(같은 가격의 원화가 한 답변에 여러 값으로 나오지 않게). 환율로 확인된 원화 금액에는 '출처 없음'을 붙이지 않는다. 환율 조회에 실패하면 고치지 않는다.
  - 환율을 보여줄 때 이용 조건에 따라 출처 'Rates By Exchange Rate API'(링크)를 표시한다.
  - 외부 API에는 통화 코드 외의 사용자 데이터(질문 내용, user_id 등)를 보내지 않는다.
- **날짜 처리**: "다음 주", "이번 주말" 같은 상대 날짜는 오늘 날짜(기본 한국 시간)를 기준으로 해석한다.
  - 상대 날짜를 실제 날짜로 바꾸는 계산은 LLM 암산이 아니라 **날짜 계산 도구(파이썬)**가 한다. LLM은 표현을 도구 인자로 옮기기만 한다.
  - **상대 날짜가 있으면 날짜 계산을 반드시 거친다** (2026-11-06 추가, TASKS Phase 8 S1-1, 사용자 결정: 강제 호출 + 요일 검사): 메시지에 '다음 주·담주·토욜·모레·N일 뒤·다음 달' 같은 표현이 있으면 프로그램이 날짜 계산 도구를 먼저 부르게 한다('오늘·내일'은 제외). 일정표를 만드는 턴에는 직전 메시지의 표현도 본다. 답변 속 '날짜(요일)'이 달력과 다르면 프로그램이 요일을 고친다.
  - 해석 규칙 (한 주는 **월요일~일요일**)
    - 이번 주: 오늘이 속한 주의 월~일
    - 다음 주: 이번 주 다음의 월~일 (예: 오늘이 11/5(목)이면 다음 주 = 11/9(월)~11/15(일))
    - 다음 주 X요일: 다음 주 월~일 안의 X요일 (예: 다음 주 토요일 = 11/14)
    - 이번 주말 / 다음 주말: 이번 주 / 다음 주의 토~일. 이번 주말 중 이미 지난 날은 빼고, 오늘이 일요일이면 오늘
    - "3일 뒤", "모레"처럼 일 단위 표현: 오늘 + N일
  - 여행 기간: 출발일과 박 수가 있으면 귀국일(출발일 + 박 수)과 일차별 날짜도 같은 도구가 계산한다.
- API 실패, 또는 날씨 예보 범위(약 2주) 밖의 날짜: RAG 문서·LLM 일반지식으로 대체하되 **대체 정보임을 표시**한다. RAG 문서는 '제목 + URL'로, LLM 일반지식은 '출처 없음, 사용자 확인 필요'로 표시한다. (예: "보통 11월 오사카는 선선해요 (출처 없음, 사용자 확인 필요)")
  - 출처 없는 가격 정보는 2.6에 따라 '(출처 없음, 사용자 확인 필요)'를 붙여 표시한다. (예산 계산은 2.3 규칙을 따른다)

### 2.5 단발성 여행 질문 Q&A·추천
- 일정 생성이 아닌 개별 질문 (예: "A 관광지 아침에 사람 많아?")
- 근거 소스: RAG(기본 KB + 사용자 수집 URL)와 웹 검색. **검색 순서는 프로그램이 고정한다** (2026-11-05 변경: 이전에는 에이전트가 도구를 골랐으나, 저장 자료를 두고 웹 검색부터 하는 경우가 있어 변경)
  1. 사용자가 저장한 자료와 기본 KB를 **먼저** 검색한다.
  2. 판정 모델이 검색 결과마다 질문과의 관련성을 판정해, **관련 없는 결과는 답변에 쓰지 않는다.** (판정이 실패하면 결과를 그대로 쓴다)
  3. 관련 결과가 하나도 없으면 자동으로 웹 검색 결과를 쓴다.
     - 저장 자료·기본 KB 검색 자체가 실패해도(권한·네트워크 장애 등) 답변을 멈추지 않고 웹 검색으로 이어간다. (2026-11-05 추가: UX 평가에서 검색 장애 시 답변 전체가 사라지고 대화가 이어지지 않는 문제 발견)
  4. 관련 결과가 있어도 부족하거나 가격·영업시간처럼 최신 정보가 필요하면, 에이전트가 웹 검색으로 보충한다. 이때도 그 턴에 1을 하지 않았으면 웹 검색 전에 1~2를 먼저 한다.
- 검색이 필요 없는 질문(날씨·환율·잡담 등)은 이 검색을 하지 않는다.
- **웹 검색은 필수 기능**이다. Q&A 외에도 예산 가격 조사(2.3), URL 수집 실패 시 대체(2.1), 기본 KB에 없는 도시 보완에 쓴다.
  - 검색 실패·할당량 초과 시: LLM 일반지식으로 대체하고 '출처 없음, 사용자 확인 필요'로 표시한다. (2.6)

### 2.6 출처·정보 원칙 (공통)
- 답변의 근거는 **'페이지 제목 + URL'** 형식으로 인용한다.
  - 예외: URL 출처가 없는 LLM 일반지식으로 대체·추정한 내용은 **'출처 없음, 사용자 확인 필요'**로 표시한다. (적용: 2.1 수집 실패 시 답변, 2.3 예산 추정치, 2.4 날씨·환율 대체 정보)
- 출처 없는 가격 정보(입장료 등)는 숨기지 않고, 가격 바로 옆에 **'(출처 없음, 사용자 확인 필요)'**를 붙여 사용자가 확인하도록 알린다. (2026-11-05 변경: 이전에는 노출 금지)
  - 일정표에서는 프로그램(파이썬)이 자유 텍스트의 가격 표현과 출처 없는 입장료 칸을 찾아 표시를 붙인다. 출처가 있는 가격은 표시 없이 '제목 + URL'과 함께 보여준다.
  - 예산 '계산'에는 별도 규칙(2.3)이 적용된다: 출처 없는 추정 금액은 큰 항목(항공·숙박·식비·현지 교통)만 'LLM 추정치(출처 없음, 사용자 확인 필요)'로 계산에 넣고, 입장료 등 그 밖의 추정치는 합계에 넣지 않는다.
- **저장 자료를 근거로 하라는 요청에 저장 자료가 쓰이지 않았을 때** (2026-11-05 추가: UX 평가에서 저장 자료 0건인데 밝히지 않고 웹 정보로 일정을 짜 '내 자료 기반'으로 오인하게 한 문제): 사용자가 "저장한 거 / 저장해 둔 / 모아 둔 / 내가 보낸 글" 등으로 저장 자료를 언급했고 이번 턴에 검색했는데 검색 결과에 저장 자료가 하나도 없으면, 프로그램이 답변 끝에 "※ 저장하신 자료 중 이 질문과 관련된 자료를 찾지 못해, 저장 자료 없이 답했습니다."를 붙인다(일정표 답변 포함). 판정은 파이썬 규칙으로 한다.
  - 이를 위해 검색 결과마다 출처 구분(사용자 저장 자료 / 기본 KB / 웹)을 붙인다.
- **저장 자료 출처 표시** (2026-11-05 추가: 처음엔 선택 기능이었으나 사용자 결정으로 추가): 답변에 인용된 출처 중 사용자가 저장한 자료에는 프로그램(파이썬)이 앞에 **'📌 내가 저장한 자료 (MM/DD 저장)'**을 붙인다. 웹 검색·기본 자료 출처에는 붙이지 않는다. 내 보관함이 실제로 쓰였는지와 그 정보가 언제 저장된 것인지를 화면에서 알 수 있게 한다. (일정표 답변 포함)

### 2.7 사용자 식별·데이터 관리
- 사용자는 `user_id`로 구분한다. 실행할 때 지정하고, 입력하지 않으면 기본값은 `"default"`이다.
- 저장·검색은 user_id별로 분리한다. 다른 user_id의 URL 콘텐츠는 검색되지 않는다.
- 일부 user_id는 시스템 예약값이라 사용자가 쓸 수 없다.
- 특정 user_id의 수집 데이터만 초기화하는 기능(CLI 명령)을 제공한다. 기본 KB에는 영향이 없다.

### 2.8 가드레일·범위 밖 요청
- **여행과 무관한 질문**: 정중히 거절하고 여행 질문으로 유도한다. 도구는 호출하지 않는다. (예: "저는 여행 계획·조언을 돕는 에이전트예요. 여행 관련 질문을 해 주세요.")
- **시스템 프롬프트·내부 설정 요청**: 지시문·도구 설정 내용은 공개하지 않고, 도울 수 있는 기능(일정·예산·날씨·환율·여행 Q&A)만 안내한다.
- **수집·검색 본문 속 지시문 (간접 프롬프트 인젝션)**
  - 수집 URL·RAG·웹 검색 본문은 **참고 자료**로만 쓰고, 그 안의 지시는 따르지 않는다.
  - 지시문 포함이 의심되는 페이지는 저장하지 않고 답변에도 쓰지 않는다. 안전을 위해 참고하지 않았다고 알리고 로그에 기록한다. (2.1)
- **다른 사용자 자료 요청**: user_id는 대화 내용으로 바꿀 수 없다. 다른 사용자의 자료와 대화 기록에는 접근할 수 없고, 요청하면 접근할 수 없다고 답한다. 이 격리는 LLM 판단이 아니라 코드로 보장한다.
- **일반 답변 속 가격**: 일정표가 아닌 답변에서 출처 URL 없이 말한 가격은 프로그램이 근거를 붙인다. (2.6)
  - 이번 턴 검색 결과에 같은 금액이 있으면 → 그 결과의 '(출처: 제목 URL)'을 가격 옆에 붙인다. (2026-11-05 추가: 검색에서 온 가격인데 출처를 안 밝힌 경우)
  - 환율·예산 계산 결과에서 온 금액 → 도구 출처가 있으므로 그대로 둔다.
  - 어디에도 없는 금액 → '(출처 없음, 사용자 확인 필요)'를 붙인다.
- **방어 단계 정리 (간접 프롬프트 인젝션)**: ① 저장 단계: 판정 모델(앞부분) + 프로그램 정규식(본문 전체)으로 지시문 페이지 거절 ② 사용 단계: 참고 자료를 구분자로 감싸고 그 안의 지시를 따르지 않는다고 지시문에 명시. 2026-11-05 점검에서 ①을 우회해 강제로 저장한 지시문도 ②에서 따르지 않음을 확인.

### 2.9 장기 기억 (추후 기능 1.5-1, 2026-11-05 설계 결정)
- **목표**: 같은 사용자(user_id)라면 대화창(thread)이 바뀌어도 이름·성향 같은 중요한 정보를 기억한다. 웹으로 확장하면 로그인 계정 ID가 user_id가 되고, 계정마다 여러 대화창이 이 기억을 함께 쓴다.
  - 구분: 대화 기록(단기)은 thread마다, 저장한 링크(RAG)와 장기 기억은 user_id마다 저장된다.
- **기억 항목** (조정 가능한 설정값): 이름·호칭 / 여행 선호(음식·숙소·관심사·여행 스타일 등) / 답변 스타일(짧게·표로 등).
- **저장 시점**: 매 턴 자동. 파이썬 규칙으로 자기 정보를 말한 것 같은 메시지만 거른 뒤, 판정 모델이 **사용자가 직접 말한 정보만** 항목별로 뽑고, 파이썬이 항목·형식을 검사해 저장한다. 추측·일시적 요청(이번 여행에만 해당하는 조건 등)은 저장하지 않는다. 저장하거나 바꾸면 답변 끝에 무엇을 기억했는지 알린다.
- **사용**: 매 턴 기억을 에이전트에게 알려 답변에 반영한다(예: 호칭으로 부르기, 선호 반영, 답변 스타일 따르기). 기억을 근거로 추천·가정할 때는 '기억한 정보'임을 밝힌다.
- **확인·삭제**: 대화 중 CLI 명령 `/memory`(기억 보기), `/forget-memory <항목>`(그 항목 지우기), `/remember <항목> <내용>`(직접 추가·수정, 아래). 프로그램이 처리하고 LLM을 거치지 않는다. `--reset`은 저장한 링크와 기억을 함께 지운다. 웹에서는 기억 패널(2.10)에서 보고 지우며, 기억 알림·대화 안내도 CLI 명령 대신 '기억' 버튼을 안내한다.
- **직접 추가·수정** (2026-11-06 추가, TASKS Phase 9 F1, 사용자 결정: 추천안대로): 대화를 거치지 않고 웹 기억 패널('추가'·'수정')이나 CLI `/remember <항목> <내용>`으로 항목을 직접 적는다. 프로그램이 처리하고 LLM을 거치지 않는다.
  - 항목은 지금처럼 3개(이름·호칭 / 여행 선호 / 답변 스타일)로 고정한다.
  - 빈 값, 200자 넘는 값(자르지 않고 알림), 지시문처럼 보이는 값(링크 저장과 같은 규칙)은 저장하지 않고 이유를 알린다.
  - 직접 적은 항목은 '직접 입력'으로 표시한다. 자동 저장은 그 문장을 그대로 둔 채 뒤에 덧붙일 때만 반영하고, 문장을 바꿔 쓰면 반영하지 않는다(바꾸려면 사용자가 직접 고친다).
  - MCP에서는 추가·수정하지 않고 CLI·웹을 안내한다.
- **격리**: 다른 user_id의 기억은 조회·수정되지 않도록 코드로 막는다.

### 2.10 웹페이지 (추후 기능 1.5-3, 로드맵 ③, 2026-11-05 설계 결정)
- **목표**: CLI와 같은 에이전트를 웹에서 쓴다. 계정 하나에 대화창(thread) 여러 개, 저장 링크·장기 기억은 계정 단위로 모든 대화창이 함께 쓴다.
- **회원가입·로그인**: 이메일·비밀번호. 이메일은 중복될 수 없다(대소문자·앞뒤 공백 무시). 비밀번호는 원문을 저장하지 않는다. 로그인 실패는 이메일 존재 여부를 드러내지 않는 같은 문구로 알린다. 로그인한 계정의 내부 ID가 에이전트 user_id다(이메일을 user_id로 쓰지 않는다).
- **화면** (클로드·ChatGPT식)
  - 왼쪽: 내 대화 목록(최근 순, 제목은 첫 질문 앞부분), 선택해 이어가기, 새 대화, 대화 삭제, 로그아웃.
  - 가운데: 채팅. 답변은 마크다운(표·굵게·링크)으로 보여 주고, 기다리는 동안 '링크 확인 중 → 자료 검색 중 → 답변 작성 중'처럼 진행 단계를 보여 준다.
  - 링크 패널: URL을 넣으면 대화와 같은 처리(수집 → 판정 → 저장)로 저장하고 ✔/✖와 이유를 보여 준다. 저장한 링크 목록(제목·URL·저장일)과 삭제(그 링크의 저장 내용 전체 삭제). 대화 입력창에 넣은 URL도 지금처럼 저장된다.
  - 기억 패널: 장기 기억 보기·직접 추가·수정·항목 삭제(CLI `/memory`·`/remember`·`/forget-memory`와 같음, 2.9).
- **격리**: 다른 계정의 대화·링크·기억은 보이지도, 열리지도, 지워지지도 않는다.
- **테마** (2026-11-05 결정, 같은 날 사용자 요청으로 A '하늘 탑승권' → B로 교체): '잉크 & 페이퍼' — 따뜻한 종이색 바탕에 먹색 글자, 강조색(남색)은 링크·진행 단계에만 쓰는 절제된 톤. 글꼴은 Pretendard. 유치해 보이던 장식(✈ 아이콘, 산호색 점, 탑승권 점선 카드)은 없애고, 진행 단계의 출발→도착 경로선만 남긴다. 프로그램 안내(✓ 저장함·✕ 못 씀·📌 저장 자료·기억 알림)는 강조색과 겹치지 않는 의미색으로 한눈에 구분되게 한다.
- **답변 글자 스트리밍** (2026-11-05 추가, 처음엔 '나중에'였으나 응답 속도 개선으로 앞당김): 답변이 만들어지는 대로 글자를 바로 보여 준다(작성 중 커서). 다 끝나면 프로그램이 링크 안내·📌·가격 출처를 붙인 최종본으로 바꿔 끼운다. 도구를 부르기 전 짧은 글('찾아볼게요')은 지운다. 일정표는 도구 결과가 최종 답변이라 진행 단계로만 보여 준다.
- **동시 사용·중지** (2026-11-06 Phase 7 R4): 답변은 대화마다 따로 만든다. 다른 사람이나 내 다른 대화가 답변 중이어도 기다리지 않는다. 다만 같은 대화에서는 답변이 끝나거나 멈춘 뒤에 보낸다. 답변 중에는 보내기 버튼이 '중지'로 바뀌고, 누르면 진행 중인 단계가 끝나는 대로 멈추며 '답변을 멈췄습니다'를 보여 준다. 새로고침하거나 다른 대화를 보다 돌아와도 답변은 끝까지 만들어지고(링크 안내·기억 저장 포함), 다시 열면 진행 상황을 이어 본다. 서버 전체의 동시 답변 수는 설정값으로 제한하고, 넘으면 '잠시 기다리는 중'을 보여 준다.
- **일정표 카드 화면·이미지 저장** (2026-11-06 결정, '나중에'에서 앞당김, TASKS Phase 7 R5-5·R5-6): 웹에서는 일정표를 줄글 대신 트리플식 카드(일차 탭, 시간대별 타임라인, 장소 사이 이동, 입장료·출처·📌 배지, 일차별 비용, 예산 요약 카드)로 보여 준다. 수정한 일정은 바뀐 항목을 강조한다. 카드는 '이미지로 저장' 버튼으로 PNG를 내려받는다(`html2canvas`). CLI·평가·복사용 줄글 일정표는 그대로 둔다.

### 2.11 MCP 서버 (추후 기능 1.5-2, 로드맵 ②, 2026-11-06 설계 결정)
- **목표**: Claude Desktop 같은 MCP 클라이언트에서 이 여행 에이전트를 쓴다. 각자 자기 PC에서 서버를 실행하는 **로컬 방식(stdio)**이다(인터넷에 공개하는 원격 서버는 범위 밖).
- **노출 방식 (혼합)**
  - **주 도구 `ask_trip_agent`**: 질문을 우리 에이전트에 그대로 넘겨 CLI와 **같은 답**(출처, 일정표 형식, 가드레일, 링크 판정·저장, 장기 기억, 가격 출처 표시)을 돌려준다. 대화는 대화 ID로 이어 쓴다(처음엔 새로 만들어 답 끝에 알려 준다).
  - **보조 계산 도구**: 예산 계산·환율 환산·날짜 계산·날씨 예보를 따로 열어, 클라이언트의 모델이 간단한 계산을 바로 부를 수 있게 한다. 계산은 CLI와 같은 파이썬 함수다(Bedrock을 쓰지 않음).
- **사용자 ID**: 서버 설정값 `MCP_USER_ID`(기본 `mcp_user`)로 **고정**한다. 대화 내용으로 바꿀 수 없다(2.8). CLI·웹 사용자의 저장 링크·기억과는 따로이고, 같이 쓰려면 `MCP_USER_ID`를 그 CLI 사용자 이름으로 바꾼다. 다른 사용자의 대화 ID를 넣으면 CLI처럼 거부한다.
- **비용·키**: 에이전트는 실행하는 PC의 `.env`(AWS Bedrock·Tavily 키)로 동작하고 비용도 그 계정에서 나간다. 저장소에 키가 없으므로, 다른 사람이 받아 쓰려면 자기 AWS 키·Bedrock 모델 권한·Tavily 키를 넣어야 한다. 클라이언트(Claude Desktop)의 사용량은 각자의 Claude 요금제에서 나간다.
- **저장 링크·기억 관리**: 목록 보기·삭제는 MCP에서 제공하지 않는다. 요청하면 CLI(`/saved`·`/memory`) 또는 웹 화면을 안내한다.
- **긴 답변**: 일정표처럼 오래 걸리는 답은 진행 단계를 클라이언트에 알려 준다(MCP 진행 알림).
