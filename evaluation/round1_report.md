## 2. 평가 방법

### 2.1 데이터 구성 (20건)
| 카테고리 | 건수 | 다룬 내용 |
|---|---|---|
| positive | 8 | 일정표, 예산 합계, 예산 초과 알림, 날씨, 환율, KB Q&A, URL과 함께 요청, 저장 URL을 새 대화에서 인용 |
| negative | 4 | 출처 없는 입장료, 예산을 말하지 않았을 때 판정 문구 금지, 무관 URL, 여행 무관 질문(코딩) |
| edge | 5 | 예보 범위 밖 날짜, 수집 실패 URL(유튜브), 정보 부족 요청, 한 메시지에 URL 6개, 같은 URL 재입력 |
| guardrail | 3 | 다른 사용자 자료 요청, 시스템 프롬프트 탈취, URL 본문 속 지시문(간접 인젝션) |

- 예산 케이스(2·3·10번)는 비용을 원화로만 주어 정답 금액을 고정했다. 정답은 실제 계산 함수(`compute_budget`)로 미리 검증했다(1,380,000 / 900,000·초과 200,000 / 690,000).
- 날씨·환율·검색처럼 값이 매번 바뀌는 케이스는 값이 아니라 **도구 호출 여부와 출처 표기**로 판정했다.
- 상태가 필요한 케이스는 `note`의 `[setup]`(user·reset·ingest·thread)으로 전제 조건을 만들었고, 시연 데이터(alice 등)를 건드리지 않도록 평가 전용 user_id(`eval_…`)를 썼다.

### 2.2 판정 방식 (EVALUATION.md 5)
- `expected_tools`: 실행 기록의 도구 호출로 확인
- `expected_traits`: 문자열 포함(`|`는 대안), `forbidden`: 문자열 미포함
- 문자열로 판정하기 어려운 항목(`~` 표시, 7개)만 Haiku 4.5가 예/아니오로 채점 — 예: '정중히 거절하고 여행 질문으로 유도함', '예산 초과 시 조정안을 제시함'
- 케이스 통과: 모든 검사 항목 충족

### 2.3 합격 기준과 URL 세트 (EVALUATION.md 6)
- 합격: 전체 80%(16건) 이상 + guardrail 3건 전부 통과
- URL: 관련(네이버 블로그 센소지 글, GO TOKYO 시부야 스카이), 무관(Python 튜토리얼), 수집 실패(유튜브, example.com), 간접 인젝션(`fixtures/inject.html`, 평가 스크립트가 로컬 웹서버로 제공 — 외부 게시 없음)

### 2.4 재현
```
python -m src.preprocess.build_kb      # 기본 KB 적재 (처음 한 번)
python -m evaluation.run_eval          # 20건 전체 실행 → results/eval_날짜시각.json
python -m evaluation.run_eval --ids 9,15   # 일부만 실행
```

## 6. UX 평가 후속 수정과 재평가 (TASKS Phase 5-2)

최종 실행 뒤, 실제 사용자처럼 CLI를 써 보는 UX 평가(URL 저장 → 새 대화에서 활용 흐름)를 했다. 평가는 **3/10**이었고 "모아 둔 블로그에 질문하면 출처와 함께 답한다"는 장점은 있지만 북마크·메모 앱보다 나을 이유가 없다는 판정이었다. 20건 평가에는 드러나지 않던 문제들이라, 고친 뒤 20건을 다시 돌려 기존 기능이 깨지지 않았는지 확인했다.

### 6.1 지적 → 수정
| UX 평가 지적 | 원인 | 수정 (TASKS) |
|---|---|---|
| 오류 한 번에 그 대화가 영구히 망가지고, "잠시 후 다시 시도"를 따라도 회복 안 됨 | 지식베이스 검색 도구 예외(임베딩 권한 오류)가 그래프 밖으로 나가, 결과 없는 도구 호출이 대화 기록에 남음 → 이후 모든 턴을 Bedrock이 거부 | 도구 예외를 오류 결과 메시지로 변환(`ToolErrorMiddleware`), 모델 호출 직전 결과 없는 도구 호출 보정(이미 깨진 대화도 복구), 오류 안내를 원인별로 분리 (T1) |
| 장애 시 링크+질문의 답변 전체가 사라짐 | 위와 같은 예외 | 지식베이스 검색 실패 시 웹 검색으로 계속 답변 (T1) |
| 링크 안내가 두 번 붙고 같은 링크의 이유가 엇갈림 | 프로그램이 붙인 안내가 기록에 남아 LLM이 다음 턴에 흉내 냄 | 모델 입력에서 안내 블록 제거, LLM이 쓴 블록 삭제 후 한 번만 붙임, 본문 언급 금지 지시 강화 (T2) |
| 시스템 장애도 링크 탓처럼 보여 멀쩡한 링크를 포기하게 함 | 저장 실패가 '처리 중 오류'로만 안내 | 저장·판정 실패는 "링크에는 문제가 없지만 … 잠시 후 같은 링크를 다시 보내 주세요"로 구분, 거절 이유 뒤에 다음 행동 안내 (T2) |
| 저장됐는지, 무엇을 저장했는지 알 수 없음 | 실패한 링크만 알림 | '※ 링크 처리 결과'에 ✔ 저장함 / ✖ 못 씀 모두 표시, 링크만 보내면 LLM 없이 저장 결과만 답함 (T3) |
| 저장 자료가 0건인데 "저장한 거 기반으로"에 그대로 진행 | 저장 자료 사용 여부를 확인하지 않음 | 검색 결과에 출처 구분(saved·kb·web)을 붙이고, 저장 자료가 안 쓰였으면 프로그램이 안내 (T3) |
| "지워줘"에 지운 척할 위험 | 목록·삭제 기능이 없음 | 미지원임을 정확히 안내하고 `--reset` 안내 (T3) |
| 링크 저장 기능을 알 방법이 없음, 개발 용어 노출 | README·시작 화면·--help에 설명 없음, '청크'·'KB' 문구 | 시작 화면·--help·README 안내, "링크 N개 확인 중…", `--reset`은 링크 수로 안내, 대화 거부 문구에 이유·다음 행동, 답변 중 Ctrl+C는 그 답변만 취소 (T4) |

- 모두 **파이썬 코드로 보장**했다(안내문 생성·블록 정리·링크만 보낸 메시지 판별·저장 자료 사용 판정). 단위 테스트 `tests/test_resilience.py`를 추가해 전체 62건이 통과한다.
- 임베딩 권한 오류 자체는 `.env`의 AWS 키 교체(새 키에 Titan 호출 권한 없음)가 원인이라 코드가 아니라 키 조치로 해결했다.

## 7. 한계와 주의
- **1회 실행 결과다.** LLM 답변은 실행마다 조금씩 달라질 수 있어, 같은 케이스가 다음 실행에서 다르게 나올 가능성이 있다. 특히 `~` 항목(7개)은 채점 모델의 판단에 의존한다.
- **실시간 값**(날씨·환율·검색 결과)은 실행 시점마다 다르다. 예: 9번의 입장료는 1차 600엔, 최종 1,200엔으로 검색된 자료가 달랐다(값이 아니라 출처 표기로 판정).
- **가격 근거 자동 표기는 숫자 일치 방식**이라, 같은 금액이 다른 맥락에서 우연히 검색 결과에 있으면 그 출처가 붙을 수 있다.
- **일정 요청 판정은 키워드 방식**이라 '일정' 같은 단어가 들어간 일정표가 아닌 질문에도 정보 확인 도구가 먼저 호출될 수 있다(되묻는 항목이 이미 다 있으면 바로 진행).
- 13번(내년 1월 1일 날씨)은 실행일이 그 날짜에서 16일 이내가 되면 예보 범위 안으로 들어와 기대 결과가 달라진다.
- 평가 대화는 실제 대화 DB에 남기지 않지만, 벡터DB에는 평가 전용 user_id(`eval_…`)의 수집 자료가 남는다(`python main.py --reset <user_id>`로 정리 가능).
- 일정표 케이스는 검색·날씨 조회·렌더링이 이어져 100초 안팎이 걸린다.
- **본문의 링크 처리 결과 언급은 프롬프트 지시로만 막는다.** 안내 블록 중복은 코드로 막았지만, LLM이 본문에서 "여행과 무관한 링크예요"처럼 한 번 더 말하는 경우가 시연 점검에서 1회 있었다(6.3). 안내 내용이 프로그램 판정과 같아 모순은 없다.
- **같은 AWS 키의 일일 토큰 한도.** 하루 사용량이 많으면 기본 모델이 한도에 걸려 대체 모델로 넘어가고, 그만큼 응답이 느려진다. 대체 순서는 Sonnet 4.5 다른 리전 → Sonnet 4.6 → Haiku 4.5라 끝까지 밀리면 답변 모델이 바뀔 수 있다(`logs/trace.jsonl`의 `model`로 확인).
